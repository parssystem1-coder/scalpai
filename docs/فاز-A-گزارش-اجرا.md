# فاز A — گزارش اجرا («انسداد را باز کن»)

> این سند فقط تغییرات **واقعاً اعمال‌شده و راستی‌آزمایی‌شده** را ثبت می‌کند.
> هر ادعا با اجرای دستور تأیید شده است، نه با فرض.
> مرجع برنامه: `docs/تحلیل-وضعیت-فازها-و-نقشه-راه-اصلاح.md`

---

## چرا فاز A اول بود؟

نقشهٔ راه قبلی مستقیم سراغ «دقت مدل» می‌رفت، در حالی که پروژه یک انسداد پایه‌ای داشت:
**ساخت نسخهٔ نصبی روی هر کلون تازه غیرممکن بود.** بهبود دقت محصولی که قابل تحویل نیست،
ارزشی برای کلینیک ایجاد نمی‌کند. علاوه بر آن، نبود CI باعث شده بود چند فاز «انجام‌شده»
علامت بخورند در حالی که کدشان هرگز وارد مخزن نشده بود.

## A1 — شفاف‌سازی وضعیت واقعی فازها

سند `docs/تحلیل-وضعیت-فازها-و-نقشه-راه-اصلاح.md` اضافه شد که شامل:
- تفکیک دو نقشهٔ راه متفاوت با شماره‌گذاری یکسان (منشأ اصلی سردرگمی)
- راستی‌آزمایی تک‌تک ادعاهای فاز ۰ در برابر کد
- جدول ردیابی هر ۳۳ آیتم نقشهٔ راه به مقصد جدیدش

**یافتهٔ کلیدی:** از ۵ آیتم ادعایی فاز ۰، تنها ۲ مورد در کد وجود داشت

لاگر فایل چرخشی، و بکاپ نسخهٔ ۳ — هیچ اثری در مخزن نداشتند.

## A3 — رفع انسداد بیلد (آیتم اصلی این فاز)

### مشکل دقیق

`electron-builder.json` به ۱۰ منبع در پوشهٔ `build/` ارجاع می‌داد؛ **هیچ‌کدام در مخزن نبودند**:

```
MISS build/icon.ico            MISS build/installerSidebar.bmp
MISS build/icon.icns           MISS build/installerHeader.bmp
MISS build/icons               MISS build/installer.nsh
```

`.gitignore` فقط `build/output/` را نادیده می‌گرفت، پس این حذف عمدی نبود — فایل‌ها
روی ماشین شخصی ساخته شده و هرگز کامیت نشده بودند. در electron-builder نسخهٔ ۲۶،
`installerIcon`، بیت‌مپ‌ها و `installer.nsh` خطای قطعی `InvalidConfigurationError`
می‌دهند و بیلد را متوقف می‌کنند.

### راه‌حل: تولید به‌جای کامیت

اسکریپت `scripts/generate-build-assets.cjs` همهٔ دارایی‌ها را از روی
`public/icon.png` (۱۰۲۴×۱۰۲۴) می‌سازد.

**چرا تولید و نه کامیت باینری‌ها؟**
- **منبع حقیقت واحد:** تغییر برند = عوض کردن یک فایل، نه شش فایل که می‌توانند واگرا شوند.
- باینری‌ها diff قابل‌بازبینی ندارند و مخزن را سنگین می‌کنند.
- خودکار در `electron:build:*` و در CI اجرا می‌شود، پس «یادمان نمی‌رود».

**بدون هیچ وابستگی جدید:** رمزگذاری PNG/ICO/ICNS/BMP دست‌ساز است
(`scripts/lib/png.cjs` و `scripts/lib/icon-formats.cjs`) تا نه به ImageMagick
(که روی همهٔ ماشین‌ها نیست) و نه به `sharp` (باینری native) نیاز باشد.

### تله‌های فرمت که عمداً رعایت شدند

| تله | چرا مهم است |
|---|---|
| ICO باید تصویر ۲۵۶×۲۵۶ داشته باشد | الزام صریح electron-builder؛ نبودش = رد بیلد ویندوز |
| در دایرکتوری ICO، اندازهٔ ۲۵۶ با بایت `0` کد می‌شود | ۲۵۶ در یک بایت جا نمی‌شود — جایی که ICOهای دست‌ساز خراب می‌شوند |
| ICNS باید کانتینر واقعی باشد | ImageMagick در برخی نسخه‌ها بی‌صدا PNG با پسوند `.icns` می‌سازد که macOS ردش می‌کند |
| BMP نصب‌کننده: BMP3، ۲۴ بیت، بدون آلفا | NSIS فرمت‌های دیگر را خراب نمایش می‌دهد |
| BMP ردیف‌ها از پایین به بالا + padding به مضرب ۴ بایت | خرابی خاموش در رندر |
| ابعاد دقیق ۱۵۰×۵۷ و ۱۶۴×۳۱۴ | NSIS ابعاد دیگر را کش می‌دهد |
| کوچک‌سازی مرحله‌ای (box filter) قبل از bilinear | بدون آن، ۱۰۲۴→۱۶ باعث aliasing شدید و آیکون «نقطه‌نقطه» می‌شود |
| «contain» به‌جای «stretch» در بیت‌مپ‌ها | کشیدگی لوگو در سایدبار نصب‌کننده غیرحرفه‌ای است |

### راستی‌آزمایی خروجی

اعتبارسنجی با تجزیهٔ مستقل باینری (نه صرفاً اعتماد به اسکریپت خودم):

```
ICO   : type=1، ۷ اندازه (۱۶ تا ۲۵۶)، هر ورودی با payload منطبق، شامل ۲۵۶ ✅
ICNS  : magic='icns'، طول هدر = اندازهٔ واقعی فایل، ۶ چانک، پیمایش دقیقاً تا EOF ✅
BMP   : ۱۵۰×۵۷ و ۱۶۴×۳۱۴، ۲۴ بیت، بدون فشرده‌سازی، اندازهٔ داده منطبق با ابعاد ✅
PNG   : میانگین رنگ ۱۰۲۴→۲۵۶→۳۲ با اختلاف ≤ ۱/۲۵۵ (تغییر اندازه وفادار است) ✅
بصری  : آیکون ۲۵۶ و ۳۲ و سایدبار BMP چشمی بازبینی شدند ✅
```

**قطعی بودن:** دو اجرای متوالی با `--force` خروجی بایت‌به‌بایت یکسان دادند،
و checksum در دو محیط مجزا یکسان بود.

### نتیجهٔ نهایی

بازتولید منطق `getResource` خودِ electron-builder روی هر ۱۰ ارجاع:

```
✅ nsis.installerIcon      ✅ nsis.installerHeaderIcon   ✅ win.icon
✅ nsis.installerSidebar   ✅ nsis.uninstallerIcon       ✅ mac.icon
✅ nsis.uninstallerSidebar ✅ nsis.include               ✅ linux.icon
✅ nsis.installerHeader
→ همهٔ ۱۰ منبع resolve شد (قبلاً: صفر)
```

> **محدودیت صادقانه:** ساخت کامل `.exe` در این محیط قابل انجام نبود، چون سندباکس
> اجازهٔ دانلود باینری‌های Electron را نمی‌دهد (`unable to verify the first certificate`).
> این یک محدودیت شبکهٔ محیط است، نه مشکل پیکربندی — خطای مربوط به دارایی‌ها کاملاً
> برطرف شده. جاب `package` در CI روی `windows-latest` این را انتها-به-انتها تأیید می‌کند.

## A4 — نگهبان خودکار (CI)

### `scripts/test-build-assets.cjs`

تستی که مانع تکرار این باگ می‌شود. نکتهٔ کلیدی: **فهرست دارایی‌ها را از خودِ
`electron-builder.json` می‌خواند**، نه از یک لیست ثابت. پس اگر فردا ارجاع تازه‌ای
اضافه شود و دارایی‌اش تولید نشود، همان‌جا قرمز می‌شود.

چهار مرحله: بازتولید از منبع ← همگامی پیکربندی با دیسک ← اعتبارسنجی ساختاری ←
بررسی `.gitignore` (تا نسخهٔ کامیت‌شده با تولیدشده واگرا نشود).

**اثبات اینکه تست واقعاً کار می‌کند** (تستی که هرگز قرمز نمی‌شود بی‌ارزش است):

| سناریو | نتیجه |
|---|---|
| افزودن ارجاع بدون دارایی | ✗ شناسایی شد، کد خروج ۱ |
| PNG با پسوند `.icns` | خودکار بازتولید و ترمیم شد |
| حالت سالم | ✅ ۱۶ بررسی، کد خروج ۰ |

### `.github/workflows/ci.yml`

| جاب | زمان اجرا | محتوا |
|---|---|---|
| `verify` | هر push و PR | tsc ← eslint ← vitest ← قرارداد DB ← ثابت‌های مشترک ← دارایی‌ها ← build |
| `package` | دستی یا تگ `v*` | ساخت واقعی نصب‌کنندهٔ ویندوز + آپلود artifact |

`--frozen-lockfile` تضمین می‌کند lockfile با `package.json` همگام بماند
(محلی تأیید شد: `Already up to date`).

## فایل‌های تغییریافته

**جدید:**
- `scripts/generate-build-assets.cjs` — تولیدکنندهٔ دارایی‌ها
- `scripts/lib/png.cjs` — رمزگشا/رمزگذار PNG + تغییر اندازه
- `scripts/lib/icon-formats.cjs` — نویسندهٔ ICO/ICNS/BMP3
- `scripts/test-build-assets.cjs` — نگهبان
- `docs/ci/ci.yml` + `docs/ci/README.md` — CI (نیازمند یک قدم دستی برای فعال‌سازی؛ پایین را ببینید)
- `build/installer.nsh` — اسکریپت NSIS (دست‌نویس، کامیت می‌شود)
- `docs/تحلیل-جامع-پروژه.md`، `docs/تحلیل-وضعیت-فازها-و-نقشه-راه-اصلاح.md`

**ویرایش‌شده:**
- `package.json` — اسکریپت‌های `build:assets` و `test:assets`؛ افزودن به `verify` و `test:all`؛ اتصال به همهٔ مسیرهای `electron:build:*`
- `.gitignore` — نادیده‌گرفتن دارایی‌های تولیدشده (با استثنای `installer.nsh`)

## ⚠️ یک قدم دستی برای فعال‌سازی CI

فایل workflow آماده است ولی در `docs/ci/ci.yml` قرار دارد، نه در `.github/workflows/`.
علت: GitHub اجازه نمی‌دهد یک GitHub App بدون مجوز `workflows` فایل workflow را
push کند (محدودیت امنیتی خود GitHub — پیام دقیق:
`refusing to allow a GitHub App to create or update workflow ... without workflows permission`).

برای فعال کردن، این را یک بار اجرا کنید:

```bash
mkdir -p .github/workflows
git mv docs/ci/ci.yml .github/workflows/ci.yml
git commit -m "ci: فعال‌سازی workflow بررسی خودکار"
git push
```

راهنمای کامل: `docs/ci/README.md`
