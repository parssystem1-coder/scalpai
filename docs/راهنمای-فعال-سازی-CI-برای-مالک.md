# راهنمای فعال‌سازی CI — گام‌به‌گام برای مالک محصول

> **این کار چیست؟** «CI» یعنی یک ربات رایگان روی گیت‌هاب که **هر بار** کدی به
> مخزن اضافه می‌شود، خودش همهٔ آزمون‌های کیفیت را اجرا می‌کند و اگر چیزی خراب
> بود، علامت قرمز می‌زند.
>
> *مثال ساده:* مثل دستگاه کنترل کیفیت انتهای خط تولید. تا امروز، فقط من
> آزمون‌ها را اجرا می‌کردم و شما مجبور بودید به گزارش من اعتماد کنید. بعد از
> این کار، **گیت‌هاب مستقل از من** همه‌چیز را می‌سنجد و نتیجه را به شما نشان
> می‌دهد.
>
> **چرا خودتان باید انجامش دهید؟** توکن دسترسی من عمداً مجوز نوشتن در پوشهٔ
> `.github/workflows` را ندارد — این یک محدودیت امنیتی استاندارد گیت‌هاب است
> (جلوگیری از اینکه یک ابزار خودکار بتواند ربات‌های خودش را تغییر دهد). پس این
> دو فایل فقط با حساب خود شما قابل فعال‌سازی است.
>
> **مدت زمان:** حدود ۵ دقیقه. **ریسک:** بسیار پایین — فقط دو فایل تنظیمات
> اضافه می‌شود و هیچ کد برنامه‌ای تغییر نمی‌کند.

---

## بخش ۰ — وضعیت فعلی (راستی‌آزمایی‌شده)

| مورد | وضعیت |
|---|---|
| فایل CI فعلی | `.github/workflows/ci.yml` — کار می‌کند ولی **۳ گام کم دارد** |
| نسخهٔ کامل آماده | `docs/release-pipeline/ci.yml` |
| ورک‌فلوی انتشار | `docs/release-pipeline/release.yml` — **اصلاً فعال نیست** |
| آخرین کامیت | `0a27e74` (پایان فاز ۳) |

**سه گامی که الان کم است** (تفاوت دقیق با `diff` گرفته شده):

```
+ node scripts/test-updater.cjs              ← آزمون سامانهٔ به‌روزرسانی خودکار
+ node --expose-gc scripts/test-backup-stream.cjs  ← آزمون حافظهٔ پشتیبان‌گیری
+ node scripts/check-changelog-version.cjs   ← قفل هماهنگی نسخه و CHANGELOG
```

> **چرا مهم‌اند؟** این سه دقیقاً همان‌هایی هستند که اگر خراب شوند، **کاربر
> نهایی** ضرر می‌کند: به‌روزرسانی خودکار از کار می‌افتد، پشتیبان‌گیری از عکس‌های
> زیاد حافظه را پر می‌کند، یا نسخه‌ای منتشر می‌شود که با فهرست تغییراتش نمی‌خواند.

## بخش ۱ — پیش‌نیازها

فقط دو چیز:

1. **Git روی کامپیوترتان نصب باشد** — برای بررسی، در Git Bash بزنید:
   ```bash
   git --version
   ```
   اگر شماره‌ای مثل `git version 2.4x.x` دید، آماده‌اید.

2. **یک‌بار قبلاً از این مخزن clone گرفته باشید.** اگر نگرفته‌اید:
   ```bash
   cd ~/Desktop
   git clone https://github.com/parssystem1-coder/scalpai.git
   cd scalpai
   ```

## بخش ۲ — دستورها (کپی و اجرا در Git Bash)

پوشهٔ پروژه را باز کنید و دستورها را **یکی‌یکی** اجرا کنید. بعد از هر دستور
خروجی را نگاه کنید؛ اگر چیزی مثل انتظار نبود، متوقف شوید و از من بپرسید.

### گام ۱ — رفتن به شاخهٔ درست و گرفتن آخرین تغییرات

```bash
git checkout arena/019fb7af-scalpai
git pull
```

**انتظار:** پیامی مثل `Already up to date` یا فهرست فایل‌های به‌روزشده.

> ⚠️ **نکتهٔ مهم:** حتماً روی همین شاخه بمانید (`arena/019fb7af-scalpai`).
> کل کار سه فاز اخیر روی همین شاخه است.

### گام ۲ — تأیید اینکه فایل‌های آماده وجود دارند

```bash
ls docs/release-pipeline/
```

**انتظار:** باید دقیقاً این دو را ببینید: `ci.yml` و `release.yml`
اگر ندیدید، یعنی گام ۱ کامل انجام نشده — دوباره `git pull` بزنید.

### گام ۳ — دیدن تفاوت، قبل از اعمال (اختیاری ولی توصیه‌شده)

```bash
diff .github/workflows/ci.yml docs/release-pipeline/ci.yml
```

**انتظار:** ۹ خط با علامت `>` که همان سه گام جدید هستند. این یعنی «دقیقاً
همین‌قدر تغییر می‌کند، نه بیشتر». اگر چیز دیگری دیدید، به من بگویید.

### گام ۴ — کپی کردن دو فایل

```bash
cp docs/release-pipeline/ci.yml .github/workflows/ci.yml
cp docs/release-pipeline/release.yml .github/workflows/release.yml
```

**انتظار:** هیچ خروجی‌ای چاپ نمی‌شود. در دنیای دستورها، **سکوت یعنی موفقیت**.

### گام ۵ — بررسی اینکه چه چیزی قرار است ثبت شود

```bash
git status
```

**انتظار:** باید ببینید `ci.yml` تغییر کرده (`modified`) و `release.yml`
فایل جدید است (`untracked`). اگر فایل دیگری در فهرست بود، متوقف شوید.

### گام ۶ — ثبت و ارسال به گیت‌هاب

```bash
git add .github/workflows/
git commit -m "ci: فعال‌سازی گام‌های تست موج ۳ و زنجیرهٔ انتشار (AUD-3/OWN-1)"
git push origin arena/019fb7af-scalpai
```

**انتظار:** خط آخر باید چیزی شبیه این باشد:
```
0a27e74..xxxxxxx  arena/019fb7af-scalpai -> arena/019fb7af-scalpai
```

اگر گیت‌هاب نام کاربری و رمز خواست: به‌جای رمز باید **Personal Access Token**
بدهید (گیت‌هاب از ۲۰۲۱ رمز عادی را نمی‌پذیرد). اگر با این مواجه شدید، بگویید
تا راهنمای جداگانه بدهم.

## بخش ۳ — تماشای نتیجه (بخش لذت‌بخش)

۱. به این آدرس بروید:
   **https://github.com/parssystem1-coder/scalpai/actions**

۲. باید یک اجرای جدید با نام **CI** ببینید که کنارش دایرهٔ **زرد** در حال
   چرخش است (یعنی در حال اجرا).

۳. رویش کلیک کنید و بعد روی **«تایپ‌چک، لینت، تست و بیلد»**. حالا گام‌ها را
   زنده می‌بینید.

۴. حدود **۳ تا ۵ دقیقه** طول می‌کشد. در پایان باید **تیک سبز ✅** ببینید.

### گام‌هایی که باید سبز شوند (۱۰ تا)

| # | گام | چه چیزی را می‌سنجد |
|---|---|---|
| ۱ | نصب وابستگی‌ها | کتابخانه‌ها درست نصب می‌شوند |
| ۲ | تایپ‌چک TypeScript | خطای نوع داده در کد نیست |
| ۳ | لینت | کیفیت و یکدستی کد |
| ۴ | تست‌های واحد | **۲۷۳ آزمون** منطق برنامه |
| ۵ | قرارداد دیتابیس | هر دو موتور ذخیره‌سازی درست کار می‌کنند |
| ۶ | 🆕 کنترلر به‌روزرسانی | سامانهٔ آپدیت خودکار سالم است |
| ۷ | 🆕 استریم بکاپ | پشتیبان‌گیری حافظه را پر نمی‌کند |
| ۸ | 🆕 قفل نسخه | نسخه و CHANGELOG هم‌خوان‌اند |
| ۹ | همگامی ثابت‌ها | دو موتور تحلیل یک نتیجه می‌دهند |
| ۱۰ | دارایی‌ها + بیلد | بستهٔ نصبی قابل ساخت است |

> **پیش‌بینی من:** هر ۱۰ گام سبز می‌شوند. من همین الان **دقیقاً همین ۱۰ دستور
> را با همان ترتیب** روی همین کد اجرا کردم و همه با کد خروجی ۰ (موفق) تمام
> شدند. اگر با این حال قرمز شد، بخش ۵ را ببینید.

## بخش ۴ — دربارهٔ فایل دوم (`release.yml`)

این یکی **الان هیچ کاری نمی‌کند** و این عمدی است. فقط وقتی فعال می‌شود که
شما یک «تگ نسخه» بسازید. یعنی با کپی کردنش هیچ اتفاق ناخواسته‌ای نمی‌افتد.

**کاری که در آینده انجام می‌دهد:** وقتی آمادهٔ انتشار بودید، با دو دستور
(`git tag v1.1.0` و `git push origin v1.1.0`) گیت‌هاب **خودش** نسخهٔ ویندوز را
می‌سازد و در بخش Releases منتشر می‌کند — همان‌جایی که برنامه برای به‌روزرسانی
خودکار نگاه می‌کند.

> ⚠️ **الان تگ نزنید.** انتشار واقعی باید بعد از فاز ۴ و ترجیحاً بعد از خرید
> گواهی امضای کد انجام شود. اگر الان تگ بزنید، نصب‌کننده‌ای منتشر می‌شود که
> ویندوز به کاربر دربارهٔ آن هشدار «ناشر ناشناس» می‌دهد.

## بخش ۵ — اگر قرمز شد (عیب‌یابی)

**اول از همه: نگران نباشید.** قرمز شدن CI هیچ آسیبی به کد یا داده نمی‌زند؛
فقط یک گزارش است.

| نشانه | معنی | کار شما |
|---|---|---|
| اصلاً هیچ اجرایی در تب Actions ظاهر نشد | ورک‌فلو شناخته نشده — معمولاً فایل در مسیر اشتباه است | بررسی کنید فایل‌ها دقیقاً در `.github/workflows/` باشند نه جای دیگر |
| خطای `Resource not accessible by integration` | مشکل مجوز | معمولاً یعنی با حساب اشتباه push شده |
| گام «نصب وابستگی‌ها» قرمز شد | مشکل موقت شبکهٔ گیت‌هاب | دکمهٔ **Re-run jobs** را بزنید |
| یکی از گام‌های تست قرمز شد | یک نقص واقعی | **اسکرین‌شات آن گام را برای من بفرستید** — عیب‌یابی و رفعش با من است |
| `git push` خطای احراز هویت داد | نیاز به Personal Access Token | به من بگویید تا راهنما بدهم |

> **قانون طلایی:** هرگز برای «سبز کردن» CI، گامی را از فایل حذف نکنید. اگر
> گامی قرمز شد یعنی واقعاً چیزی خراب است — پاک کردن آزمون، مشکل را حل نمی‌کند
> بلکه فقط پنهانش می‌کند.

## بخش ۶ — بعد از سبز شدن، چه چیزی عوض می‌شود؟

۱. **استقلال از گزارش من.** تا امروز وقتی می‌گفتم «همهٔ گیت‌ها سبز است»، شما
   باید به حرفم اعتماد می‌کردید. از این پس یک تیک سبز روی گیت‌هاب دارید که
   **مستقل** آن را می‌سنجد. این دقیقاً همان چیزی است که قاعدهٔ «انجام شد یعنی
   همهٔ گیت‌ها سبز» را قابل‌اثبات می‌کند.

۲. **کشف زودهنگام خرابی.** اگر هر تغییری در آینده چیزی را بشکند، همان لحظه
   معلوم می‌شود — نه هفته‌ها بعد در کلینیک.

۳. **AUD-3 و OWN-1 بسته می‌شوند.** دو مورد از فهرست ممیزی حذف می‌شوند و
   می‌توانم سند پیگیری را به‌روز کنم.
