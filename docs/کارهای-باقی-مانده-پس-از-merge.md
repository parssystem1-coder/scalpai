## ⚠️ ترتیب را رعایت کنید

اگر ترتیب را جابه‌جا کنید، یا هیچ اتفاقی نمی‌افتد یا نسخهٔ اشتباه منتشر می‌شود:

```
۱. ادغام PR به main                    ← AUD-16 حل می‌شود
۲. تأیید فعال شدن ورک‌فلوی Release
۳. حذف تگ قدیمی v1.1.0                 ← AUD-20 (مهم!)
۴. خرید گواهی امضای کد + سکرت‌ها        ← OWN-4
۵. بالا بردن نسخه به 1.2.0
۶. زدن تگ v1.2.0                       ← OWN-2
۷. تست به‌روزرسانی روی ویندوز           ← OWN-3
```

## قدم ۱ — ادغام Pull Request

در صفحهٔ PR (لینکش را در چت دریافت کرده‌اید) دکمهٔ **Merge pull request** را
بزنید.

یا از Git Bash:

```bash
cd مسیر-پروژه
git checkout main
git pull
git merge arena/019fb7af-scalpai
git push origin main
```

> **بی‌خطر است:** ادغام به‌تنهایی هیچ ریلیزی نمی‌سازد. ریلیز فقط با «تگ» فعال
> می‌شود که در قدم ۶ است.

## قدم ۲ — تأیید فعال شدن ورک‌فلوی انتشار (AUD-16)

```bash
gh workflow list
```

**پیش از ادغام** فقط یکی را می‌دیدید:
```
CI    active    322348475
```

**پس از ادغام** باید هر دو را ببینید:
```
CI         active    ...
Release    active    ...
```

**چرا این‌طور است:** گیت‌هاب ورک‌فلوهایی را که با «تگ» فعال می‌شوند، فقط از
شاخهٔ پیش‌فرض (`main`) می‌شناسد. تا فایل `release.yml` به `main` نرسد، زدن تگ
هیچ کاری نمی‌کند — بدون هیچ پیام خطایی.

> اگر `Release` را ندیدید، قدم ۱ کامل انجام نشده. جلوتر نروید.

## قدم ۳ — حذف تگ قدیمی 🔴 (AUD-20) — **این را جا نیندازید**

**مشکل کشف‌شده:** یک تگ `v1.1.0` از قبل روی مخزن هست، ولی روی کامیت `f515313`
— یعنی **پیش از شروع هر پنج فاز اصلاح**.

آن نسخه **هیچ‌کدام از این‌ها را ندارد**:
- رفع نشت عکس بیمار به پوشهٔ موقت ویندوز
- پسورد اجباری فایل پشتیبان
- تب ردپای حسابرسی
- رفع قفل‌شدن آپلود عکس

**خطر:** حالا که ورک‌فلوی Release فعال شده، اگر آن تگ به هر دلیلی دوباره پوش
شود، **نسخهٔ ناامن قدیمی منتشر می‌شود**.

```bash
# حذف از سرور
git push origin --delete v1.1.0

# حذف از کامپیوتر خودتان
git tag -d v1.1.0

# تأیید — نباید چیزی برگرداند
git ls-remote --tags origin | grep v1.1.0
```

## قدم ۴ — گواهی امضای کد (OWN-4) 🔴 برای فروش حیاتی است

**چرا نمی‌شود نادیده گرفت:** بدون امضا، ویندوز به پزشک هشدار **«ناشر ناشناس»**
می‌دهد. بسیاری در همان لحظه نصب را لغو می‌کنند. این یک مانع فروش است، نه فقط
یک ایراد فنی.

**هزینه:** حدود ۲۰۰ تا ۴۰۰ دلار در سال (گواهی OV).

پس از خرید، فایل `.pfx` را به base64 تبدیل و به‌عنوان سکرت ثبت کنید:

```powershell
# در PowerShell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\path\to\cert.pfx")) | Set-Clipboard
```

سپس در گیت‌هاب: **Settings → Secrets and variables → Actions → New secret**

| نام سکرت | مقدار |
|---|---|
| `CSC_LINK` | همان رشتهٔ base64 |
| `CSC_KEY_PASSWORD` | پسورد فایل pfx |

> اگر این سکرت‌ها نباشند، بیلد **خطا نمی‌دهد** — فقط نسخهٔ امضانشده می‌سازد.
> پس حتماً پیش از انتشار نهایی تنظیمشان کنید.

جزئیات کامل: `docs/release.md` بخش ۳.

## قدم ۵ — بالا بردن نسخه به ۱٫۲٫۰

سه چیز باید هم‌زمان عوض شوند، وگرنه گارد `check-changelog-version.cjs` جلوی
انتشار را می‌گیرد:

**الف) `package.json`:**
```json
"version": "1.2.0",
```

**ب) `CHANGELOG.md`** — عنوان `## [منتشرنشده]` را به این تغییر دهید:
```
## [1.2.0] - 2026-08-XX
```
(تاریخ روز انتشار)

**ج) تأیید:**
```bash
node scripts/check-changelog-version.cjs
```
باید سبز شود.

> **چرا ۱٫۲٫۰ و نه ۱٫۱٫۰؟** چون تگ `v1.1.0` قبلاً روی کامیت دیگری مصرف شده و
> استفادهٔ دوباره‌اش سردرگمی می‌سازد. ضمناً این نسخه تغییرات محصولی واقعی دارد
> (پسورد اجباری بکاپ، تب حسابرسی) که یک نسخهٔ minor را توجیه می‌کند.

سپس این تغییر را کامیت و پوش کنید:
```bash
git add package.json CHANGELOG.md
git commit -m "chore(release): نسخهٔ 1.2.0"
git push origin main
```


سپس به تب **Actions** بروید. ورک‌فلوی **Release** باید خودکار شروع شود و حدود
۲۰ تا ۴۰ دقیقه طول بکشد (ساخت نصب‌کنندهٔ ویندوز).

## قدم ۷ — تست به‌روزرسانی خودکار (OWN-3)

روی یک ویندوز تمیز (ترجیحاً ماشین مجازی):

1. نسخهٔ قدیمی‌تر را نصب کنید
2. برنامه را باز کنید و چند دقیقه صبر کنید
3. باید بنر «نسخهٔ جدید موجود است» ظاهر شود
4. به‌روزرسانی را بزنید و مطمئن شوید بدون خطا نصب می‌شود
5. **مهم:** بعد از به‌روزرسانی، داده‌های قبلی باید سر جایشان باشند

چک‌لیست کامل: `docs/release.md` بخش ۴.
