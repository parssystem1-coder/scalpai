```
┌─────────────────────────── Electron Main (main.cjs) ───────────────────────────┐
│  قفل تک‌نمونه → setName → CSP → initDatabase (SQLite یا fallback JSON)         │

│  ├─ schema-migrations.cjs (۸ نسخه)       ├─ db-common.cjs (منطق مشترک)         │
│  ├─ ai-handlers.cjs (net + پروکسی session، کلید فقط اینجا)                     │
│  ├─ offline-handlers.cjs (Python subprocess/exe با timeout و kill)             │
│  ├─ auth-session.cjs (توکن درون‌حافظه‌ای ۱۲ساعته، بدون دیسک)                    │
│  └─ path-allowlist.cjs (fs فقط مسیرهای دیالوگ‌گرفته)                            │
└───────────────▲────────────────────────────────────────────────────────────────┘
        preload.cjs (contextBridge — ۷ سطح API، بدون nodeIntegration)
┌───────────────┴──────────────────── Renderer (React+Vite) ─────────────────────┐
│  App.tsx (lazy pages + RequireAuth) → MainLayout → ۱۲ صفحه                     │
│  store/ (۷ Zustand store با صفحه‌بندی و anti-race)                             │
│  db/ ← DatabaseAdapter: Electron IPC | adapter-web (localforage)               │
│  lib/ ← سه موتور: aiProvider/aiRequestCore | scalpFeatures/offlineAnalysis     │
│         | localModel (TF.js، lazy-loaded ۱.۶MB chunk)                          │
└────────────────────────────────────────────────────────────────────────────────┘
```

## ۴. لایهٔ Electron — فایل‌به‌فایل

### ۴.۱ `electron/main.cjs` (۹۶۴ خط) — نقاط قوت
1. **قفل تک‌نمونه + `second-instance`**: جلوگیری از دو اتصال به یک SQLite — درست.
2. **`app.setName('ScalpAI')` قبل از قفل**: رفع باگ واقعی تاریخی (دو پوشهٔ userData مختلف dev/prod) — نشانهٔ تیمِ از-تجربه-آموخته.
3. **fallback سه‌مرحله‌ای دیتابیس**: sqlite → JSON با دیالوگ توضیح فارسی، + `migrateJsonFallbackIntoSqlite()` که حتی پسورد/کلید safeStorage-رمزنگاری‌شده را در مهاجرت حفظ می‌کند و فایل JSON را بازنشسته (نه حذف) می‌کند — تعامل کاربرِ غیرفنی عالی.
4. **CSP دوحالته dev/prod** با `wasm-unsafe-eval` فقط برای TF.js؛ `setWindowOpenHandler` فقط http/https؛ `will-navigate` مسدود؛ DevTools در prod غیرفعال.
5. **API key هرگز از renderer پذیرفته نمی‌شود** (`resolveAiConfig` همه‌چیز را از DB در main می‌خواند) — دفاع در برابر renderer آلوده، فراتر از استاندارد رایج.
6. **پنجرهٔ چاپ/PDF مجزا** با preload مخصوص و پاکسازی فایل temp.

### ۴.۱.۲ نقاط ضعف/ریسک‌های `main.cjs`
- **`exportData`/`importData` بزرگ در main-in-memory**: بکاپ همهٔ عکس‌ها **و ویدیوها** را base64 می‌کند و `JSON.stringify(..., null, 2)` یک‌باره می‌سازد. با چند صد عکس ۲-۵MBای، رشتهٔ چندگیگابایتی در حافظهٔ main → کرش یا فریز چندده‌ثانیه‌ای. **پیشنهاد:** بکاپ استریمی (zip با فایل‌های جدا) یا حداقل هشدار حجم + صف.
- **`setFullScreen(true)` اجباری در شروع**: کلینیک شاید بخواهد کنار سیستم نوبت‌دهی کار کند؛ ترجیحاً از تنظیمات/state قبلی پیروی شود.
- **`proxyUrl` از renderer پذیرفته می‌شود**؛ تهدید کم (اپ محلی) ولی ترکیب با «AI از طریق net همان session» یعنی proxy تنظیم‌شده ترافیک AI را هم می‌بلعد — که البته **عمداً و مستند** است (پروکسی سیستم برای ایران)؛ OK، فقط صراحتش را در UI نگه دارید.
- **`previewTmpPath`/`printWin.__scalpaiCleanup`**: نگهداری state روی آبجکت پنجره با property سفارشی — شکننده در برابر ریفکتور؛ بهتر Map ضعیف.

### ۴.۲ `electron/preload.cjs` (۸۰ خط) — ✅ الگوی درست
contextBridge با ۷ namespace کوچک، بدون send/sync، بدون افشای ipcRenderer خام. `platform`/`isElectron` به‌درستی از طریق contextBridge و window. نکتهٔ مثبت: encrypt/decrypt عمومی **عمداً حذف شده** تا سطح حمله کم شود.

### ۴.۳ `electron/db-handlers.cjs` (۱۱۰۵ خط) — قلب داده
**قوت:** prepared statement همه‌جا (بدون تزریق SQL)، path traversal clientId مسدود (`saveImageToFile`)، thumbnail caching، `stripAnnotatedImage` برای جلوگیری از صدها مگابایت IPC در لیست‌ها، مهاجرت پسورد legacy با timing-safe-compare، orphan-drop در import با لاگ، حذف فایل‌های تازه‌ساخته در catch، و ۵۳ متد قراردادی.
**ضعف/ریسک:**
- `analyses.aiResults/offlineResults` شامل `annotatedImageBase64` (PNG 300-800KB) داخل TEXT دیتابیس — با هزاران تحلیل، دیتابیس چند GB؛ بهتر فایل شود مثل gallery.
- `training_samples.imageThumbnail` هم base64 در DB — در fetch لیست نمونه‌ها درج می‌شود (مقیاس ضعیف).
- `previousGallery` فایل‌ها بعد از commit حذف می‌شوند؛ کرش بین commit و حذف = فایل یتیم (جزئی).
- بدون rate-limit روی `verifyCredentials` — بروت‌فورس پسورد محلی نامحدود (ریسک کم چون لوکال، ولی یک‌خط سطر تأخیر ارزشش را دارد).

### ۴.۴ `electron/db-handlers-json.cjs` (۶۵۸ خط) + `src/db/adapter-web.ts` (۶۲۵ خط)
🔴 **بزرگ‌ترین بدهی فنی پروژه: سه پیاده‌سازی کامل و هم‌ترازِ ۵۳ متد.**
تست قرارداد (`test-db-contract.cjs`) انحراف رفتاری را می‌گیرد و `db-common.cjs` هش/بکاپ/sanitize را مشترک کرده — این یعنی تیم از درد آگاه است. ولی منطق صفحه‌بندی، فیلتر، ترتیب، و قوانین import/export **سه‌بار** نوشته شده و هر ویژگی جدید باید سه‌بار پیاده شود.
**پیشنهاد ساختاری (مهم‌ترین توصیهٔ این سند):**
- کوتاه‌مدت: بیشتر منطق را به `db-common.cjs` منتقل کنید (فیلتر/صفحه‌بندی/sanitize خروجی به‌صورت pure functions روی آرایه‌ها) تا duet SQLite/JSON فقط لایهٔ ذخیره باشد.
- بلندمدت: نسخهٔ وب را هم به SQLite ببرید (`sql.js` یا `wa-sqlite` روی OPFS) — آن‌وقت **یک** schema + **یک** لایهٔ کوئری برای هر سه محیط؛ adapter-web می‌میرد و فقط wrapper IPC/لوکال می‌ماند.

### ۴.۵ `electron/schema-migrations.cjs` (۲۹۸ خط) — ✅ از بهترین فایل‌ها
نسخه‌گذاری schema با تراکنش، تشخیص دیتابیس قدیمی بدون جدول نسخه، ردیف سیستم استخر آموزشی idempotent — الگوی درست صنعتی.

### ۴.۶ `electron/auth-session.cjs` + `path-allowlist.cjs` + `ai-handlers.cjs` + `offline-handlers.cjs`
- auth: توکن ۳۲بایتی، TTL، بدون دیسک — درست برای اپ تک‌کاربرهٔ محلی.
- allowlist: نرمال‌سازی، دفاع NUL-byte/dir-traversal — درست.
- ai-handlers: استفاده از `net` الکترون (پروکسی session خودکار)، abort واقعی با requestId، timeout جدا، پیام فارسی برای اشتباه رایج کاربران (کلید OpenRouter روی سرویس Gemini) — **سطح تعاملی بالاتر از حد انتظار**.
- offline-handlers: تشخیص exe بسته‌بندی‌شده → script→ fallback مرورگر، timeout ۶۰ثانیه + SIGTERM/SIGKILL، پاکسازی temp در finally.
  ⚠️ مسیر exe فقط ویندوز (`ScalpAI-Python-Analyzer.exe`)؛ روی mac/linux پایتون‌سیستم + cv2 لازم است وگرنه بی‌صدا به موتور مرورگر می‌افتد — مستند است ولی برای کراس‌پلتفرم واقعی باید PyInstaller per-OS.

## ۷. سه موتور هوش — جمع‌بندی مستقل من

(جزئیات کامل در `docs/تحلیل-عمیق-سه-موتور.md`؛ اینجا تأیید/افیاده‌های تازهٔ من)

1. **آنلاین (Vision LLM):** مهندسی درخواست/امنیت/خطا در سطح A است. تأیید می‌کنم: نبود متر «AI vs Expert» یعنی انتخاب مدل/سرویس هنوز حدس است؛ و اعتبارسنجی فقط schema-سطح است نه محتوایی (bbox خارج از تصویر، تناقض score↔observation).
2. **آفلاین (Heuristic/Python TS parity):** فاز ۱ (نرمال‌سازی نور/گرید تطبیقی/کیفیت تصویر) اعمال و با تست parity پایدار است — بازدید من از کد: گردکردن `np.round` برای برابری با Uint8ClampedArray حتی در جزییات رعایت شده. سقف دقت همچنان مقید است: ۵۹ آستانهٔ دستی روی ۱۲ فیچر آماری؛ Q-fix بزرگ بعدی: segmentation واقعی مو/پوست (HSV یا مدل سبک) قبل از فیچر تراکم/پوشش.
3. **ML محلی (TF.js MLP چندوظیفه‌ای):** مهندسی داده A- (client-split، champion/challenger، featureVersion-guard، dispose دقیق)، آمار C+ با دادهٔ کم: ۷۵ کلاس نادر با BCE بدون وزن + آستانهٔ ثابت ۰.۴۵ + F1 میکرو گمراه‌کننده؛ و گپ champion/challenger برای v3→v3 (هر «آموزش» وزن قبلی را بی‌قید بازنویسی می‌کند). فاز ۰.۱ سند فازبندی دقیقاً همین را هدف گرفته — **این اولویت اول است**.

## ۱۰. آیا «بهتر از این می‌شد»؟ — پاسخ صریح به سؤال شما

**از نظر انتخاب تکنولوژی (Electron + React + SQLite + TF.js):** برای یک اپ کلینیک تک‌کاربرهٔ آفلاین‌محور فارسی، این ترکیب **دفاع‌پذیر و درست** است؛ جایگزین‌ها (Tauri سبک‌تر اما اکوسیستم ضعیف‌تر برای SQLite/TF؛ Flutter دسکتاپ جایگزینی برای بازنویسی کامل) تغییری در مسائل واقعی (دقت تحلیل، چرخهٔ داده، توزیع) ایجاد نمی‌کردند. **نباید بازنویسی کنید.**

**کجا می‌شد بهتر بود (و هنوز می‌توان):**
1. **یک لایهٔ داده، نه سه‌تا** — مهم‌ترین تصمیم معماری آینده.
2. **تحلیل تصویر قوی‌تر**: امروز سقف دقت = سقف ۱۲ فیچر پیکسلی. مسیر ارتقا به ترتیب بازده/ریسک:
   - الغ) segmentation مو/پوست (HSV/άستانه + morphology در OpenCV.js یا همین Python) → دقت density/patchiness فعلی.
   - ب) embedding از مدل ازپیش‌آموزش‌دیدهٔ سبک (MobileNetV3 روی tfjs) به‌عنوان فیچر مکمل همان MLP — سقف دقت واقعی‌تر بدون از دست دادن explainability heuristic.
   - ج) در بلندمدت، ONNX Runtime Web با یک مدل segmentation کوچک اختصاصی (مگر دادهٔ برچسب‌خوردهٔ lesion زیاد شود).
3. **دیسیپلین ارزیابی:** K-fold cross-validation بر اساس مشتری (به‌جای split تک)، گزارش per-class PR/F1، و گیت کیفیت برای همهٔ ارتقاها — قبل از هر تغییر معماری مدل.
4. **تحلیل آنلاین:** معیار کیفیت واقعی (AI vs Expert از دادهٔ تأییدشدهٔ موجود)، اعتبارسنجی محتوایی خروجی، دی‌دوپ تصویر با هش، retry با backoff — همه کوچک و پر‌اثر.
5. **توزیع و بهره‌برداری:** electron-updater (حتی با مخزن خصوصی/Nexus داخلی)، electron-log، Sentryِ self-hosted اختیاری.
